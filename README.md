# КАИ Расписание

Веб-приложение для расписания занятий вуза.

Проект предназначен для двух ролей:

- студент: выбирает вуз, группу и подгруппу, после чего смотрит расписание;
- администратор: задаёт шаблон расписания на семестр и при необходимости переопределяет расписание для конкретной недели.

README написан как техническая карта проекта. Его цель не только описать запуск, но и быстро передать контекст другому разработчику или другой нейросети.

## 1. Что делает проект

Приложение решает задачу расписания с двумя уровнями данных:

1. базовый шаблон семестра;
2. фактические изменения для конкретных недель.

Для вуза это важно, потому что реальное расписание часто похоже на шаблон, но может меняться на следующую неделю или на отдельный период.

Сейчас проект покрывает такие сценарии:

- выбор университета, группы и подгруппы;
- просмотр расписания в веб-интерфейсе;
- расчёт чётной/нечётной недели по дате начала семестра;
- задание шаблона на семестр;
- загрузка расписания на текущую или конкретную неделю;
- ручное редактирование и удаление занятий через админку.

## 2. Ключевая бизнес-модель

### 2.1 Сущности

- `university` — вуз;
- `group` — учебная группа;
- `subgroup` — подгруппа `0`, `1`, `2`;
- `lesson` — запись о занятии;
- `semester_start_date` — дата начала семестра, используется для расчёта чётности недели.

### 2.2 Шаблон и weekly override

В текущей реализации таблица `lessons` хранит и шаблон, и недельные переопределения.

- шаблон семестра:
  - `specific_week = NULL`
  - `week_type = 0 | 1 | 2`
  - `0 = каждую неделю`
  - `1 = нечётная`
  - `2 = чётная`

- недельное переопределение:
  - `specific_week = N`
  - означает фактическое расписание для конкретной недели `N`

### 2.3 Очень важное правило текущей логики

Текущее поведение override не является "частичным патчем" недели.

Сейчас логика такая:

- если для недели `N` существует хотя бы одна запись `specific_week = N`, то фронтенд считает, что для этой недели действует override;
- в этом случае шаблонные занятия `specific_week = NULL` для этой недели больше не используются;
- значит weekly override по факту является заменой всей недели для группы, а не добавлением нескольких изменений поверх шаблона.

Практический вывод:

- если загружается расписание на конкретную неделю, нужно загружать сразу полную неделю для этой группы;
- если загрузить только один изменённый день, остальные дни этой недели могут оказаться пустыми.

Это не баг документации, а текущее реальное поведение системы. Любой агент, который будет менять доменную логику, должен знать это в первую очередь.

- React 19

- Vite

### Backend

- Express 5
- JWT
- `httpOnly` cookie для админской сессии

### База данных

### Почему SQLite оставлен

Для текущего сценария SQLite допустим:

- мало администраторов;
- проект работает на одном сервере;
- чтений больше, чем записей;
- объём данных сравнительно небольшой.

SQLite не стоит использовать, если проект будет работать в нескольких инстансах приложения, в serverless-среде или с высокой конкуренцией записи.

## 4. Архитектура проекта

### 4.1 Общая схема

- `src/` — React-приложение;
- `client-public/` — стили и ассеты Vite;
- `server/` — Express API, авторизация, сидирование, работа с БД;
- `data/` — SQLite-файл базы;
- `dist/` — production build фронтенда.

### 4.2 Как это работает

В development:

- Express API работает на `http://localhost:3000`;
- Vite frontend работает на `http://localhost:5173`;
- Vite проксирует `/api` на backend.

В production:

- сначала выполняется `vite build`;
- Express раздаёт содержимое `dist/`;
- сайт и API доступны с одного origin.

### 4.3 PWA и офлайн-режим

В публичной части проекта уже включён базовый PWA-слой:

- `manifest.webmanifest` позволяет установить приложение на домашний экран телефона;
- `service-worker.js` кеширует app shell и статические ассеты;
- публичные `GET`-запросы расписания и справочников кешируются по принципу "сначала сеть, потом кеш";
- админка и `api/admin` в кеш service worker не кладутся.

Практический смысл:

- если студент уже открывал расписание онлайн, повторный запуск приложения будет быстрым;
- при отсутствии интернета приложение попытается отдать последнюю сохранённую версию расписания;
- в development service worker не регистрируется, чтобы не мешать Vite/HMR.

## 7. API

### 7.1 Публичное API

- `GET /api/universities`
  - список вузов

- `GET /api/universities/:id/groups`
  - список групп выбранного вуза

- `GET /api/schedule/:groupId?subgroup=1&date=2026-04-22`
  - возвращает все занятия группы и вычисленную метаинформацию по неделе

Ответ содержит:

- `group`
- `week_number`
- `week_type`
- `week_type_label`
- `semester_start`
- `lessons`
- `by_day`

Важно:

- backend не вычисляет финальное расписание по дням на все даты;
- он отдаёт данные группы и метаинформацию;
- финальная сборка недель/дней делается на фронтенде.

### 7.2 Админское API

- `POST /api/admin/login`
- `POST /api/admin/logout`
- `GET /api/admin/session`
- `GET /api/admin/groups`
- `POST /api/admin/schedule/upload` — загрузка для одной группы
- `POST /api/admin/schedule/upload-bulk` — загрузка для всех групп разом
- `GET /api/admin/lessons?group_id=...`
- `PUT /api/admin/lessons/:id`
- `DELETE /api/admin/lessons/:id`
- `GET /api/admin/settings`
- `PUT /api/admin/settings`

## 8. Формат JSON для загрузки расписания

### Одна группа

```json
{
  "university": "КНИТУ-КАИ",
  "group": "23113",
  "target_week": "template",
  "lessons": [
    {
      "day": 1,
      "subgroup": 0,
      "time_start": "09:40",
      "time_end": "11:10",
      "subject": "Высшая математика",
      "room": "305 каб.",
      "type": "Лекция",
      "teacher": "Иванов И.И.",
      "week_type": "all"
    }
  ]
}
```

### Все группы разом (bulk)

```json
{
  "target_week": "template",
  "groups": [
    {
      "university": "КНИТУ-КАИ",
      "group": "23113",
      "lessons": [...]
    },
    {
      "university": "КНИТУ-КАИ",
      "group": "23114",
      "lessons": [...]
    }
  ]
}
```

Bulk-загрузка атомарная: либо все группы записываются, либо ни одна. Лимит — 100 групп за запрос. Фронтенд автоматически определяет формат по наличию поля `groups` и отправляет на нужный endpoint.

Допустимые значения:

- `day`: `1..7` (7 = воскресенье)
- `subgroup`: `0 | 1 | 2`
- `week_type`: `all | odd | even`
- `target_week`:
  - `"template"` — обновить базовый шаблон;
  - `"current"` — обновить текущую неделю;
  - `N` — обновить конкретную неделю по номеру.

### Поведение загрузки

Оба endpoint'а делают replace, а не merge.

- если `target_week = "template"`, удаляются все шаблонные записи группы `specific_week IS NULL`, затем вставляется новый шаблон;
- если `target_week = "current"` или число, удаляются все записи этой группы для `specific_week = N`, затем вставляется новый набор.

## 9. Фронтенд: как строится расписание

Самая важная логика находится в `src/pages/SchedulePage.jsx`.

Фронтенд:

1. получает выбранную группу и подгруппу из `localStorage`;
2. запрашивает у backend данные группы и метаинформацию о неделе;
3. сам строит набор дней, начиная с выбранной даты;
4. для каждого дня определяет, использовать шаблон или weekly override.

Это значит, что изменения в доменной логике расписания почти всегда затрагивают два места:

- `server/routes/api.js`
- `src/pages/SchedulePage.jsx`

Если менять только backend или только frontend, можно сломать согласованность отображения.

## 11. Авторизация и безопасность

### Что уже сделано

- JWT хранится в `httpOnly` cookie;
- `localStorage` для админского токена больше не используется;
- cookie-authenticated admin-запросы защищены CSRF-токеном;
- есть rate limiting на логин;
- есть базовые security headers:
  - `CSP`
  - `X-Frame-Options`
  - `X-Content-Type-Options`
  - `Referrer-Policy`
  - `Permissions-Policy`
- для `/admin` и `/api/admin` выставляется `Cache-Control: no-store`.

### Что важно знать

- cookie path ограничен `/api/admin`;
- backend поддерживает чтение токена и из `Authorization`, и из cookie;
- основная схема сейчас — cookie-based session через JWT.

### Что ещё не реализовано

- нет разграничения ролей;
- нет полноценного журнала версий расписания с откатом;
- нет внешнего perimeter-контроля уровня VPN/reverse proxy; `ADMIN_ALLOWED_IPS` есть, но этого недостаточно для hardened production.

## 12. Конфигурация через env

См. `.env.example`.

Поддерживаются:

- `NODE_ENV`
- `PORT`
- `TRUST_PROXY` — опционально, только если приложение стоит за reverse proxy
- `ADMIN_ALLOWED_IPS` — опционально, список IP через запятую, которым разрешён доступ к админке
- `BACKUPS_DIR` — опционально, каталог для резервных копий SQLite
- `JWT_SECRET`
- `ADMIN_USERNAME`
- `ADMIN_PASSWORD`
- `ADMIN_COOKIE_NAME` — опционально

### Важно

- в production `JWT_SECRET` обязателен;
- в production сидирование без `ADMIN_PASSWORD` запрещено;
- в development при отсутствии `JWT_SECRET` сервер генерирует временный секрет, из-за чего админская сессия сбросится после рестарта.

## 14. Очень важное предупреждение про сидирование

`server/seed.js` сейчас не является нейтральным bootstrap-скриптом. Это dev/demo seed.

Он делает следующее:

- создаёт/обновляет один конкретный вуз;
- оставляет только группы из фиксированного списка;
- создаёт или обновляет админа;
- ставит `semester_start_date`;
- удаляет все записи из `lessons`;
- затем загружает тестовые шаблоны чётной/нечётной недели.

Это значит:

- `npm run seed` нельзя бездумно запускать на боевой базе;
- на production он может стереть рабочие данные расписания.

Если проект будет реально передаваться вузу, seed нужно в будущем разделить на:

- безопасный bootstrap;
- отдельный dev/demo seed.

## 16. Ограничения и технический долг

### 16.1 Нет сущности semester

Сейчас дата начала семестра хранится одной записью в `settings`.

Это упрощение. Для боевого использования лучше иметь отдельную таблицу семестров:

- `semester`
- диапазон дат
- активный семестр
- шаблоны, привязанные к семестру

### 16.2 Override — это замена недели, а не точечный diff

Это уже описано выше, но повторить важно:

- weekly override сейчас — полная подмена недели;
- если нужна модель "поменять только одну пару в среду", текущая схема это явно не поддерживает.

### 16.3 Журнал изменений пока базовый

Сейчас уже есть audit log ключевых действий администратора, но этого всё ещё недостаточно для полноценного отката и строгого контроля изменений.

Пока ещё не закрыты вопросы:

- хранение версий расписания для отката;
- экспорт/архивация журнала;
- расширенный diff "что именно поменялось" для массовых загрузок.

### 16.4 Тестовое покрытие пока точечное

Сейчас есть smoke/contract тесты на часть критичных сценариев, но серьёзные изменения в логике недель и overrides всё ещё требуют расширения покрытия.

## 17. Рекомендованный следующий этап развития

Если проект становится реальным вузовским сервисом, я бы двигался так:

1. Добавить сущность `semester`.
2. Разделить:
   - шаблоны семестра;
   - weekly overrides;
   - историю изменений.
3. Усилить audit log и добавить удобный diff изменений.
4. Довести backup SQLite до автоматической стратегии и регламента хранения.
5. Усилить доступ к админке на уровне reverse proxy/VPN.
6. Написать тесты на критическую доменную логику:
   - вычисление недели;
   - odd/even;
   - поведение override;
   - загрузку шаблона;
   - загрузку конкретной недели.

- лучше сохранить прозрачную доменную логику, чем прятать её в слишком сложный ORM или абстракции;
- любые изменения в weekly override должны сопровождаться явным описанием новой семантики;
- перед запуском на production нельзя полагаться на дефолтные секреты и dev seed.

## 20. Короткий итог

Это уже рабочий веб-проект расписания с React/Vite, Express и SQLite.

Его главная доменная особенность:

- есть шаблон семестра;
- есть фактические переопределения на конкретные недели;
- текущая реализация интерпретирует weekly override как замену всей недели для группы.

Если другой агент начинает работу над проектом, он должен сначала проверить, устраивает ли эта семантика бизнес-заказчика. Это самый важный контекст проекта.
